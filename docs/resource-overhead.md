# CPU 与内存优化记录（2026-09-10）

以下先记录第一轮优化，后续增量结果见文末。前三轮优化已纳入 `20260910` 完整 dist（Java 0.3.2、Node.js/Python 0.2.3），第四轮随后纳入 `20260910-r2` 完整 dist（Java 0.3.3、Node.js/Python 0.2.4）。默认采集范围、速率及容量上限不变；SBOM 上报仍使用简化依赖结构，本地继续保留 CycloneDX。既有归档保持原样。下文数据是各轮优化时的历史测量，发布验证另见对应包的 `release-validation.json`。

## 实现

- Node.js SBOM 根据规范化包目录建立索引，沿已观察文件的父目录查找最近包根。此前每个文件都会遍历全部组件；现在工作量取决于组件数量和文件目录深度。嵌套依赖、同名前缀、符号链接、URL query 和后续文件删除仍按现有语义处理。
- Node.js SBOM worker 不再额外保留已发布的完整组件对象和路径映射；仍保留生成历史所需的记录，主线程继续持有查询映射。
- Node.js 导出队列在入队时已复制事件；编码阶段复用这份独立副本，只有截断时复制顶层字段。调用方后续修改输入不会改变待导出内容，截断也不会修改原事件。
- Python 污点标记是不可变对象；查询时无来源歧义便复用标记元组，写入时仅在范围或单位需要规范化时复制标记。来源歧义、范围裁剪及回收规则保留。
- Python 元数据刷新用发行包名称索引关联顶层模块，避免每个模块名称都遍历全部发行包。
- Java 污点对象查找复用一个查询键，避免每次查找创建弱引用。查询由请求状态锁串行保护，结束后立即清除查询键中的强引用；实际索引继续使用弱引用。

## 受控热点测量

在 OrbStack Linux/arm64 上，以 A-B-B-A-A-B 顺序运行修改前后版本，各取三轮中位数。Node.js 24.11.1 和 Java 17 使用独立的 1 CPU / 2 GiB 容器；Python 3.11 使用同一既有 QA 容器，未调整资源限制。宿主机仍有其他工作负载。

| 场景 | 修改前 CPU 时间 | 修改后 CPU 时间 | 降幅 |
| --- | ---: | ---: | ---: |
| Node SBOM：1,000 个安装依赖、800 个文件观察，重复刷新 5 次 | 3,056 ms | 102 ms | 96.7% |
| Node 编码：10,000 条包含 128 个传播节点的事件 | 753 ms | 321 ms | 57.3% |
| Python：250,000 次标记查询和写入，每值 8 个标记 | 1,886 ms | 234 ms | 87.6% |
| Java：10,000,000 次对象身份查询 | 43.2 ms | 26.1 ms | 39.5% |

Node SBOM 测量使用真实目录及 worker，以文件 URL 提交观察；它不是执行 800 次业务模块导入的端到端测试。修改前后生成的 SBOM 内容摘要一致。事件编码测试只衡量编码函数，不包含 OTel 传输或后端接收。

内存结果须区分对象分配和进程 RSS：

- Java 上述查询循环的线程累计分配量从 **320,000,152 bytes 降为 152 bytes**；这表示减少临时对象及 GC 压力，不代表常驻内存下降 320 MB。弱引用载体回收和请求预算释放检查通过。
- Python 20 个状态、每状态 128 个载体、每载体 8 个可共享标记的合成场景，`tracemalloc` 记录的保留分配从 **2,535,714 降为 631,132 bytes**，约下降 75.1%。这是该场景的对象分配，不是整个应用内存。
- Node SBOM 场景的进程 RSS 中位数约为 **126.0 → 124.9 MiB**，变化较小；不能据此声称 Node 应用整体内存大幅降低。

## 第二轮增量优化（2026-09-10）

本轮基线已经包含上文的第一轮优化，以下降幅不能与第一轮百分比直接相加。修改覆盖六个生产文件：

- Python SBOM 元数据缓存只保存后续使用的有界许可证信息，释放完整 `METADATA` 对象及其项目说明、依赖声明等文本。生成本地组件记录时复制许可证，缓存到期仍重新读取元数据。
- Python 按原始配置值缓存模块前缀的解析结果，最多八项；每次仍读取当前环境变量。请求内的采集检查直接使用配置判定，避免重复解析与重复探测运行时，并保留探测异常时关闭采集的行为。
- Node.js 缓存当前进程不变的 Node 版本/线程支持判定；采集检查省去诊断对象创建及重复探测。环境开关、loader 状态、插桩状态和暂停仍实时生效。
- Java 每次 SBOM 刷新按 URL 对象身份去重 CodeSource，避免为同一制品的每个类重复解码和规范化路径；读取一次 ProtectionDomain/CodeSource。去重集只存在于本次刷新，不跨刷新保留类或类加载器，也不调用可能触发 DNS 的 URL 值比较。Agent 入口即使晚于同源的其他类出现，仍会将相应制品标记为基础设施。

沿用 OrbStack Linux/arm64，以 A-B-B-A-A-B 顺序各测三轮，以下均为中位数。基准与回归测试分开运行；宿主机的其他工作负载未停止。Node 24.11.1、Java 17 使用 1 CPU / 2 GiB 容器，Python 3.11.16 使用既有 QA 容器。

| Node 采集开关检查 1,000,000 次，CPU | 671 ms | 217 ms | -67.6% |
| Java 10,000 个已加载类、20 个共享制品，刷新 50 次的当前线程 CPU | 194 ms | 49 ms | -74.6% |

## 第三轮增量优化（2026-09-10）

本轮基线包含前两轮优化。本轮保留三个生产文件的改动：

- Python SBOM 的历史比较改为保存每个组件的规范化 SHA-256 摘要，释放上一版完整组件字典；快照内容未变时直接返回，不再复制整张历史表。
- Node SBOM 同样用摘要进行历史比较；一次发布复用已经构造的组件记录，供本地 CycloneDX、依赖上报和历史比较使用，减少重复构造与序列化。
- Java SBOM 的哈希结果改为直接进行十六进制编码，去除每个字节一次的 `String.format`。哈希算法和输出内容相同。

这些摘要只是进程内比较状态，不改变本地 CycloneDX、简化依赖上报、历史字段或容量配置。Python/Node 仍在文件发布成功后提交新的比较状态；更新失败不会推进修订号，恢复后可以重试。新增回归覆盖未变化组件的时间戳、删除与重新出现、许可证变更和写入失败恢复。

### 依赖较多的后台工作

OrbStack Linux/arm64，A-B-B-A-A-B，各三轮中位数。Node 24.11.1 和 Java 17 使用 1 CPU / 2 GiB 容器；Python 3.11.16 使用既有 QA 容器。性能测量期间未并行运行本任务的回归测试，宿主机其他任务保持运行。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| Python：1,000 个依赖 fixture，SBOM 刷新后保留分配 | 7.21 MiB | 5.23 MiB |
| Python：12 次不变刷新，CPU | 1,362 ms | 1,332 ms |
| Python：12 次加载观察变化，CPU | 1,784 ms | 1,715 ms |
| Node：1,000 个安装依赖、800 个加载观察，12 次映射变化发布，CPU | 432 ms | 332 ms |
| Node：同场景 12 次不变刷新，CPU | 209 ms | 208 ms |
| Java：50,000 次 1 KiB 内容 SHA-256 与编码，当前线程 CPU | 357 ms | 36 ms |
| Java：同一哈希场景的累计分配 | 893.29 MiB | 34.20 MiB |

Python 的 `tracemalloc` 保留分配下降约 **27.5%（1.98 MiB）**，测量包括元数据、历史及发布状态，不是仅估算被删除的字典。Node 变化发布的 CPU 下降 **23.1%**；不变刷新基本无变化。Java 哈希热点 CPU 下降 **89.9%**、累计分配下降 **96.2%**，不等于 JVM RSS 降幅。

Node worker 的 GC 后 heapUsed 在首次发布时约 8.00 → 7.26 MiB，但结束时约 6.94 → 7.44 MiB；RSS 三轮有重叠。因此本轮不认定 Node 整进程或持续堆占用明确下降。测量副本仅追加 worker GC/内存读数消息，不改变生产发布逻辑。

Java 的 1,000 制品完整刷新另行预热 50 次，再分别测量 20 次不变刷新和加载集合变化。不变刷新 CPU 88 → 93 ms，变化刷新 264 → 243 ms，GC 后保留堆约 6.04 → 6.06 MiB。这个端到端场景没有支持整个 JVM 内存下降或稳定 CPU 提升；最终收益集中在哈希编码热点。Java 初始五次预热的记录也保留，不能与最终充分预热的结果混合。

Python 使用真实 `.dist-info` 目录及模块观察；Node 运行真实 worker 和安装目录，通过增加 URL 观察触发发布；Java 制品测试使用真实 JAR 和已定义类，由 Instrumentation 代理提供类数组。修改前后的组件/依赖摘要以及直接哈希结果一致。

## 第四轮：远端报告后的增量优化（2026-09-10）

本轮以包含前三轮优化的源码为基线，针对远端报告提示的 Python 后台刷新、重复证据开销和文件读取降级进行改进。远端报告没有附原始 CPU profile，本地测量不能代替同机远端复测，也不能直接从报告中的插件增量 CPU 减去下表百分比。

- Python SBOM 在一次刷新中复用安装根目录的规范化结果及模块匹配结果；共享安装目录只解析一次，减少重复路径检查。只对实际候选包准备根目录，并且每轮重新检查符号链接和文件类型。路径替换、卸载、可编辑安装及发布失败重试规则保留。
- Python 和 Node 在请求结束时先判断代表样本是否需要更新，再复制详细来源、传播图、范围和调用栈。未到采样时间仍更新发生次数、最新请求/trace、验证任务的请求数与风险来源计数。原始请求证据和公开 sink 返回值保持完整，新验证任务及采样周期到期仍输出完整样本。本轮没有延迟 sink 时的首次传播图或调用栈构造。
- Python 没有污点输入的普通调用不再创建返回值传播模型。`join` 的生成器观察保留，因为污点可能在消费生成器时出现。
- Python 将标准 `Path.read_text/read_bytes` 建模为消费路径的调用：文件 sink 继续观察路径，文件内容不继承路径字符的污点，避免这类标准读取产生 `unmodeled_call_result`。自定义方法重写仍报告未知调用边界，不通过删除降级标志掩盖未知行为。
- Java SBOM 复制缓存组件时复用不可变名称、purl 和组件引用，避免重复编码及哈希。可变位置/许可证集合仍独立复制，没有增加类或 ClassLoader 的强引用缓存。

### 受控热点与内存

OrbStack Linux/arm64，A-B-B-A-A-B 各三个独立进程，表中为中位数。Python 3.13.15 使用既有 QA 容器；Node 24.11.1 和 Java 17 使用 1 CPU / 2 GiB 容器。性能测量与本任务的回归测试串行，宿主机其他任务保持运行。

| 场景 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| Python SBOM：1,000 个依赖、800 个模块观察，12 次不变刷新 CPU | 1,874 ms | 860 ms | -54.1% |
| Python SBOM：同环境 12 次加载集合变化刷新 CPU | 2,299 ms | 1,264 ms | -45.0% |
| Python 重复 finding：128 个传播节点、5,000 次请求结束处理 CPU | 978 ms | 144 ms | -85.2% |
| Node 重复 finding：同类场景 CPU | 304 ms | 59.9 ms | -80.3% |
| Java SBOM：1,000 个制品，20 次不变刷新当前线程 CPU | 91.5 ms | 81.9 ms | -10.4% |
| Java 同场景当前线程累计分配 | 165.45 MiB | 146.05 MiB | -11.7% |

重复 finding 基准测量 ledger 的请求结束处理，使用预先构造的证据，不包含首次 sink 取证、网络传输或完整 HTTP 请求。双方均保留 128 个节点的完整代表样本，累计发生次数相同。Python 另行在 100 次处理中测量 `tracemalloc` 峰值，约 65.6 → 29.1 KiB；这反映局部临时分配，不能解读为进程 RSS 降幅。

Python SBOM 的 GC 后保留分配基本持平（约 6.06 → 6.08 MiB），该合成场景 RSS 峰值约 48.68 → 49.07 MiB；本轮临时索引主要换取 CPU 收益，不能声称 SBOM 的常驻内存进一步下降。修改前后组件内容摘要一致。

Java 加载集合变化时的 20 次刷新 CPU 为 239 → 226 ms，累计分配 204.42 → 183.83 MiB；GC 后保留堆约 6.24 → 5.65 MiB。该基准真实生成 JAR 和定义类，由 Instrumentation 代理提供类数组，不衡量 JVM 枚举类的实际成本，也不代表整个 JVM RSS；依赖上报摘要相同。

Node 重复 finding 场景 GC 后堆占用基本持平。本轮减少临时复制，未证明解决远端约 120 MiB 的常驻内存增量。另一次启动拆分探测中，独立进程的 bare/compiler/runtime/full RSS 约为 43.7/65.1/97.3/125.5 MiB；仅用于定位后续 profile 方向，不能相加归因或当作完整应用测量。此次保留后台 I/O 与 SBOM worker，避免将其序列化、文件访问和扫描工作移回主事件循环。

### 持续 100 QPS 的完整 FastAPI 服务

Python 3.13 + FastAPI + OTel + SecurityContext + SBOM，额外提供相同的 1,000 个安装依赖 fixture，每份 SBOM 均为 1,063 个组件。两个版本分别启动三个独立进程，A-B-B-A-A-B 顺序；等待首次 SBOM，预热 100 次，再按 100 QPS 发送 2,000 次真实请求，约 20 秒，覆盖多次默认 5 秒后台刷新。使用最多 4 个客户端线程，采集上限保持默认 1000/s。业务为字符串传播与参数化内存 SQLite 查询，不等同于远端报告的五类混合业务。

| 三轮中位数 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 服务进程 CPU / 2,000 次请求 | 6.65 s | 6.37 s |
| 服务进程 CPU，占一个逻辑核 | 33.26% | 31.86% |
| 请求 p95 | 5.67 ms | 5.70 ms |
| 请求 p99 | 7.01 ms | 7.51 ms |
| 测量期 RSS 峰值 | 126.96 MiB | 128.05 MiB |

该完整进程 CPU 时间下降约 **4.2%**，小于热点降幅。RSS 峰值增加约 **1.09 MiB（0.9%）**，p99 增加约 0.50 ms；本轮不能声称整体内存或尾延迟下降。Node/Java 的整体应用 RSS 也尚未验证改善。临时分配、GC 后保留堆与进程 RSS 必须分别判断，后续应在远端同一业务与环境复测这个取舍。

六轮均返回预期响应；每轮包含 1 次就绪请求、100 次预热和 2,000 次测量请求，来源/sink 计数一致，活动请求归零，无预算跳过、投递丢失或请求不完整记录。未连接生产 Collector。退出使用 SIGTERM，返回码 -15，不据此推断生产后端接收或长时间内存稳定性。初次持续请求探测在源码最终冻结前主动终止，保留在 `pre-final-probes/`，不参与正式汇总；最终 HTTP 的 after 组使用冻结的源码副本。
